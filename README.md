# Tarih Backend

Бэкенд проекта «Исламская хронология»: NestJS 11, PostgreSQL, Prisma 6. Node.js 22 или новее.

## Локальный запуск

```bash
npm ci
cp .env.example .env
docker compose up -d db
npm run prisma:generate
npm run prisma:deploy
npm run start:dev
```

Сервер: http://localhost:3001/api. Проверка запуска: `GET /api/health`.
Prisma подключается к базе при запуске; без доступной базы сервер не запустится.
Health возвращает состояние процесса, а не отдельную проверку доступности базы.

## Команды

- `npm run build` — сборка.
- `npm run typecheck` — проверка TypeScript.
- `npm run start:prod` — запуск собранного приложения.
- `npm run prisma:validate` — проверка схемы.
- `npm run prisma:migrate -- --name change_name` — создание и применение новой миграции локально.
- `npm run prisma:deploy` — применение существующих миграций.
- `npm run prisma:studio` — локальный редактор данных.

## Модель данных

`Era` ↔ `Person` и `Person` ↔ `Specialty` — многие ко многим.
Один человек может относиться к нескольким эпохам и иметь несколько специальностей.
Мазхабы хранятся отдельно от специальностей, в массиве enum Madhhab. Источники — в PersonSource.
Даты пока сохраняются исходными строками, включая приблизительные и спорные датировки.
Для вычислений над датами впоследствии нужны отдельные числовые поля.

Реализованы создание и список личностей с фильтрами. Пользовательская авторизация, редактирование, удаление, админка и перенос данных сайта ещё не реализованы.
Существующий фронтенд не изменён.

## Переменные окружения

См. `.env.example`. `DATABASE_URL` обязателен; `PORT` по умолчанию 3001.
`CORS_ORIGINS` — разрешённые адреса фронтенда через запятую.
Пароль и проброс порта в compose предназначены для локальной разработки.
Для сервера задайте отдельные секреты и настройки PostgreSQL.


## API личностей

`POST /api/people` создаёт личность. Требует `Authorization: Bearer <PERSON_WRITE_TOKEN>`.
Задайте длинный случайный ключ в окружении сервера. Не добавляйте его в браузерный код.
Без настроенного ключа запись отключена (503); неверный или отсутствующий ключ — 401.
Это временный доступ для наполнения через серверный скрипт/Postman, до пользовательской авторизации.

Пример тела (вымышленная запись для демонстрации формата):

```json
{
  "slug": "example-person",
  "name": "Пример личности",
  "honorific": "Почётное обращение",
  "birthHijri": "ок. 100",
  "deathHijri": "180",
  "cities": ["Багдад"],
  "madhhabs": ["hanafi"],
  "eras": [{ "slug": "example-era", "title": "Пример эпохи" }],
  "specialties": [{ "slug": "muhaddith", "title": "Мухаддис" }],
  "sources": [{ "title": "Название источника", "url": "https://example.com/book" }]
}
```

Обязательны `slug`, `name` и хотя бы одна эпоха. Slug: латинские строчные буквы,
цифры и одиночные дефисы между словами, до 100 символов.
Дополнительные строки: `description`, `dateNote`, `birthGregorian`, `deathGregorian`.
Неизвестные поля и некорректные значения отклоняются с 400.
Эпохи и специальности подключаются по slug, отсутствующие создаются в той же транзакции.
Название существующего справочника не изменяется. Повторяющийся slug личности — 409.
При конкурентном создании одного справочника возможен 409: запрос можно повторить.
Мазхабы: `hanafi`, `maliki`, `shafii`, `hanbali`; они не являются специальностями.

`GET /api/people` — публичный список. Без query: все личности, первая страница,
20 записей, сортировка по имени и затем id по правилам сортировки PostgreSQL.

| Query | Поведение |
| --- | --- |
| `q` | Подстрока в имени и городах; без учёта регистра, ё/е; пробелы по краям убираются |
| `category` | Совместимость с клиентом: slug специальности либо мазхаб; `all` снимает этот фильтр |
| `era` | Slug эпохи |
| `specialty` | Slug специальности |
| `madhhab` | Один из четырёх мазхабов |
| `page` | Целое от 1 до 1000000, по умолчанию 1 |
| `limit` | Целое от 1 до 100, по умолчанию 20 |

Все переданные фильтры соединяются через AND. Пустой `q` не ограничивает список.
Неизвестный slug фильтра даёт пустую выдачу; некорректный query — 400.
Пример: `/api/people?category=muhaddith&era=example-era&q=Багдад&page=1&limit=20`.
Ответ: `{ "items": [], "total": 0, "page": 1, "limit": 20, "totalPages": 0 }`.
Каждая запись содержит поля Prisma, `eras`, `specialties`, `sources`, а также
`birth`, `death`, `categories` для клиентской карточки. Для подключения фронтенда
нужно отдельно заменить импорт статических данных запросами и преобразовать группировку эпох.
Сравнение современников пока остаётся на клиенте и не является серверным фильтром.

Поиск выполняет параметризованный SQL-запрос, затем фильтрует кандидатов через Prisma.
Для текущего объёма данных этого достаточно; при росте потребуется индексируемое поисковое поле.

## Проверки

- `npm test` — сборка и юнит-тесты валидации.
- `TEST_DATABASE_URL=postgresql://... npm run test:integration` — HTTP-тесты с PostgreSQL после сборки.

Каждый интеграционный запуск создаёт отдельную случайную схему, применяет миграции,
проверяет API и состояние БД, затем удаляет только свою схему.
Тестовому пользователю нужны права на создание схем.
CI запускает оба набора на PostgreSQL 16.
